# OCR

**OCR**（**Optical Character Recognition**、光学文字認識）は、**紙をスキャンした画像や写真に写っている文字を読み取って、コンピュータで扱える文字のデータ（テキスト）にする** 技術。

- 画像のままでは、検索も、コピーも、読み上げもできない。OCR をかけると、それができるようになる
- 「光学」は、光（スキャナーやカメラ）で読み取ることを指す。磁気で読む MICR と区別する言い方

## 処理の流れ

| 段階 | すること | 例 |
| --- | --- | --- |
| 1. **前処理** | 画像を読み取りやすくする | **二値化**（白と黒に分ける。大津の方法など）、**傾きの補正**、ノイズの除去、解像度をそろえる |
| 2. **レイアウト解析** | 文字のある場所と、読む順番を決める | 段組み、見出し、表、図、縦書き・横書きの判定 |
| 3. **行・文字の切り出し** | 行に分け、さらに文字（または単語）に分ける | 文字どうしがくっついたり、1 字が割れたりするのが難しい |
| 4. **認識** | 切り出した形が、どの文字かを決める | 候補をいくつか、確からしさ（スコア）つきで出す |
| 5. **後処理** | 前後の文字や辞書を使って、まちがいを直す | 「東京都」の「京」が「亰」と出たら直す、など |

いまの深層学習の OCR は、3〜5 をまとめて、**行の画像から文字の列を直接出す** ことが多い（下の「方式」）。

## 方式の移り変わり

| 方式 | しくみ | 時代 |
| --- | --- | --- |
| **テンプレート照合** | 文字の見本の形と重ねて、いちばん似たものを選ぶ | 初期。決まった字体（OCR 専用の書体）向き |
| **特徴抽出** | 線の向き・交わり・穴の数などの特徴を数にして、統計的に分類する | 1970〜2000 年代の主流 |
| **ニューラルネットワーク（CNN）** | 文字の画像を学習して分類する。LeCun の **LeNet** は、手書きの数字（小切手・郵便番号）を読んだ | 1990 年代〜 |
| **CNN＋RNN＋CTC**（CRNN） | 行の画像を左から右へ読み、文字の切れ目を決めずに文字列を出す。**CTC** は、出力と正解の文字の位置がずれていても学習できるしくみ | 2010 年代〜。Tesseract 4 以降もこの型（LSTM） |
| **Transformer** | 画像から文字列を「翻訳」するように出す（TrOCR など） | 2020 年代〜 |
| **視覚と言語の大規模モデル**（VLM） | 画像を見て、文章として書き起こす。表やレイアウトも説明できる | 2020 年代〜。ただし、**ない文字をそれらしく作ってしまう**（ハルシネーション）ことがある |

## 似た技術

| 名前 | 正式名 | 読むもの |
| --- | --- | --- |
| **ICR** | Intelligent Character Recognition | **手書き** の文字（とくに、枠の中に 1 字ずつ書いたもの） |
| **HTR** | Handwritten Text Recognition | 手書きの **文章**（続け字、古文書） |
| **OMR** | Optical Mark Recognition | **マークシート** の塗りつぶし |
| **MICR** | Magnetic Ink Character Recognition | 小切手の下の、**磁気インク** で印刷した数字（E-13B などの書体） |
| バーコード・QR コード | | 文字ではなく、決まった模様。OCR より確実に読める |

## OCR のための書体

| 書体 | 年 | 特徴 |
| --- | --- | --- |
| **OCR-A** | 1960 年代後半（アメリカの規格） | 機械が読みやすいように、角ばった独特の形。人には読みにくい |
| **OCR-B** | 1968 年 | スイスの **アドリアン・フルティガー** がデザイン。人にも読みやすい。のちに ISO の規格。**バーコードの下の数字** や、パスポートの機械読み取り欄（MRZ）に使われる |

## 日本語の OCR が難しいわけ

- **文字の種類が多い**：英語は大文字・小文字・数字で 100 字足らず。日本語は、常用漢字だけで 2,136 字、JIS 第 1・第 2 水準で 6,355 字の漢字に、ひらがな・カタカナ・記号が加わる
- **形の似た字が多い**。形だけではほぼ区別できず、**前後の文字**（カタカナの中か、漢字の中か）で決める

| 似た字 | 種類 |
| --- | --- |
| ロ／口 | カタカナ／漢字 |
| カ／力 | カタカナ／漢字 |
| ニ／二 | カタカナ／漢字 |
| エ／工 | カタカナ／漢字 |
| タ／夕 | カタカナ／漢字 |
| ヘ／へ | カタカナ／ひらがな |
| ー／一／－ | 長音／漢字／マイナス |
- **縦書き** と横書きが混ざる。**ルビ**（ふりがな）が本文の横に入る
- 単語の間に **空白がない** ので、切れ目が分かりにくい
- 古い本は、**旧字体・変体仮名・活字のかすれ** がある

## 主な OCR ソフト・サービス

| 名前 | 種類 | 備考 |
| --- | --- | --- |
| **Tesseract** | オープンソース | 1980 年代に HP が開発。**2005 年にオープンソース** になり、その後 Google が開発を支えた。日本語（`jpn`、縦書きは `jpn_vert`）も読める |
| **OCRmyPDF** | オープンソース | Tesseract を使って、スキャンした PDF に **透明テキスト** を重ねる |
| **NDLOCR** | オープンソース | **国立国会図書館** が、デジタル化した資料を読むために開発し、2022 年に公開。古い本の日本語に強い |
| ABBYY FineReader | 市販 | 精度が高い OCR ソフトとして知られる |
| Adobe Acrobat | 市販 | PDF の OCR |
| Google Cloud Vision・Amazon Textract・Azure AI Vision | クラウドの API | Textract は表や帳票の項目の取り出しにも強い |
| **macOS・iOS の「テキスト認識表示」**（Live Text） | OS の機能 | 写真や画面の文字を、そのまま選んでコピーできる |
| Google レンズ | アプリ | カメラで写した文字の読み取りと翻訳 |

### Tesseract の使い方の例

```sh
# 画像を読んで out.txt に書き出す（日本語＋英語）
tesseract scan.png out -l jpn+eng

# 縦書き
tesseract tate.png out -l jpn_vert

# スキャンした PDF を、文字を検索できる PDF にする
ocrmypdf -l jpn input.pdf output.pdf
```

- 精度を上げるには、**300 dpi 程度** でスキャンし、傾きを直し、余白や影を減らすとよい

## 透明テキスト（検索できる PDF）

- スキャンした PDF は、ページが **画像** なので、文字を検索できない
- OCR の結果を、**見えない文字** として画像の上の同じ位置に重ねると、見た目は元のまま、**検索・コピー** ができる。これを **透明テキスト** という
- 書籍の **自炊**（自分で本を裁断してスキャンする）でよく使う

## 精度の測り方

| 指標 | 意味 |
| --- | --- |
| **CER**（文字誤り率） | 正解の文字列に直すのに必要な、文字の **置き換え・抜け・余分** の数を、正解の文字数で割る。日本語ではこちらを使う |
| **WER**（単語誤り率） | 同じことを単語で数える。英語などで使う |

- 「認識率 99%」でも、1 ページ 1,000 字なら **10 か所** まちがう。そのため、大事な文書は人の確認（校正）が欠かせない

## 歴史

| 年 | できごと |
| --- | --- |
| 1910 年代 | 文字を音に変えて、目の見えない人が読む機械（**オプトフォン**） |
| 1920〜30 年代 | 文字を光で読み取る機械の特許（グスタフ・タウシェクなど） |
| 1950 年代 | アメリカで、商用の文字読み取り機が使われはじめる |
| **1968 年** | 日本で **郵便番号** が始まり、**東芝** の **郵便番号自動読取区分機** が使われる。手書きの数字を読み、郵便物を自動で分ける |
| 1970 年代 | **レイ・カーツワイル** が、いろいろな書体を読める OCR と、目の見えない人のための **読み上げ機** を作る |
| 1990 年代 | パソコンの OCR ソフトが広まる。LeNet が小切手の数字を読む |
| 2005 年 | Tesseract がオープンソースになる |
| 2010 年代 | 深層学習で精度が大きく上がる。スマートフォンのカメラで読めるようになる |
| 2020 年代 | Transformer や VLM による OCR。NDLOCR の公開（2022 年） |

## AI で OCR する

画像を理解できる大規模言語モデル（**VLM**、マルチモーダル AI）に、画像や PDF を渡して **書き起こさせる** 方法。従来の OCR より、**手書き・崩れたレイアウト・表・縦書き・古い本** に強いことが多い。

### やり方

| やり方 | 例 | 向いている場面 |
| --- | --- | --- |
| **チャットに貼る** | Claude・ChatGPT・Gemini に画像や PDF を添付して「書き起こして」と頼む | 数ページを手早く。プログラムは要らない |
| **API で呼ぶ** | プログラムから画像を送り、結果を受け取る（下の例） | 何百ページもまとめて処理する |
| **自分のパソコンで動かす** | 公開されている VLM を **Ollama** などで動かす。深層学習の OCR ライブラリ（PaddleOCR、EasyOCR、Surya など）を使う | 外に出せない文書。費用をかけたくない |
| **クラウドの文書解析** | Google Document AI、Azure AI Document Intelligence、Amazon Textract | 請求書・帳票から **決まった項目** を取り出す |

### プロンプトのこつ

```text
この画像の文字を、そのまま書き起こしてください。
- 要約や言いかえをしない。誤字も原文のまま残す
- 読めない字は推測で埋めず、〓 にする
- 改行・段落・見出しは原文のとおりに。表は Markdown の表にする
- 縦書きは、右の行から順に読む
- ルビは「漢字《かんじ》」の形で書く
- 書き起こした文字だけを出力する
```

- **「推測で埋めない」「読めない字は印をつける」** と書くのが大事。書かないと、AI は意味が通るように **それらしい字を作ってしまう**（ハルシネーション）
- **1 回に 1〜数ページ** にする。一度に多く渡すと、途中を飛ばしたり、まとめてしまったりしやすい
- 画像は、文字がはっきり読める大きさで渡す。小さい字は、ページを切り分けて拡大する

### API の例（Python・Claude）

```python
import base64
import anthropic

client = anthropic.Anthropic()  # 環境変数 ANTHROPIC_API_KEY などを使う

PROMPT = "この画像の文字を、そのまま書き起こしてください。読めない字は推測せず 〓 にしてください。書き起こした文字だけを出力してください。"

with open("scan.png", "rb") as f:
    data = base64.standard_b64encode(f.read()).decode("utf-8")

response = client.beta.messages.create(
    model="claude-opus-5-5",
    max_tokens=16000,
    output_config={"effort": "medium"},
    betas=["server-side-fallback-2026-07-01"],
    fallbacks="default",  # 断られたときに別のモデルで再試行する
    messages=[{
        "role": "user",
        "content": [
            # PDF なら {"type": "document", "source": {"type": "base64", "media_type": "application/pdf", "data": ...}}
            {"type": "image", "source": {"type": "base64", "media_type": "image/png", "data": data}},
            {"type": "text", "text": PROMPT},
        ],
    }],
)

if response.stop_reason == "refusal":
    print("断られた")
else:
    print("".join(b.text for b in response.content if b.type == "text"))
```

- PDF は、そのまま `document` として送れる（1 回 600 ページまで、32 MB まで）。ただし、精度のためには数ページずつ送るほうがよい
- たくさん処理するときは、**Message Batches**（非同期で、料金が半分）が使える

### 従来の OCR との使い分け

| | 従来の OCR（Tesseract など） | AI（VLM） |
| --- | --- | --- |
| 活字のきれいな文書 | 十分に読める。速くて安い | 読める |
| 手書き・崩れたレイアウト・表 | 苦手 | **強い** |
| まちがい方 | 似た字の取りちがえ、文字化け。**まちがいが目立つ** | 意味の通る別の字や語にする。**まちがいに気づきにくい** |
| 文字の **位置**（座標） | 出せる。**透明テキスト** を作れる | ふつうは出せない。透明テキストには向かない |
| 費用・時間 | 無料。パソコンで動く | クラウドの API はページごとに料金がかかる |
| 秘密の文書 | 手元で完結する | クラウドに送ることになる（手元で動かす VLM なら別） |

- **検索できる PDF を作るなら従来の OCR**、**読みやすいテキストがほしいなら AI**、と分けるとよい
- 両方を組み合わせる方法もある：Tesseract の結果と AI の結果を **比べて（diff をとって）**、食いちがう所だけ人が確かめる

### 確かめ方
- 数字・固有名詞・日付は、**必ず原文と見比べる**。AI は、もっともらしい数字に書きかえてしまうことがある
- 行の数や段落の数が原文と合っているかを見る。**行の飛ばし** や **くり返し** に気づける
- 大事な文書は、2 回書き起こさせて（または別のモデルで）比べる

## 押さえどころ
- OCR は、**画像の文字をテキストにする** 技術。流れは **前処理 → レイアウト解析 → 切り出し → 認識 → 後処理**
- いまは深層学習で、**行の画像から文字列を直接出す** 方式が主流
- 日本語は **字の種類が多く、似た字が多く、縦書き・ルビがある** ので難しい。似た字は、前後の文字で決める
- 手書きは ICR・HTR、マークシートは OMR、小切手の磁気インクは MICR
- スキャンした PDF に OCR をかけて **透明テキスト** を重ねると、検索できる
- 精度が高くても、まちがいは必ず残る。大事なものは人が確かめる
- AI（VLM）の OCR は、手書きや表に強いが、**まちがいがもっともらしくて気づきにくい**。プロンプトで「推測で埋めない」と指示し、数字や固有名詞は原文と見比べる

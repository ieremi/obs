# Unix 盆栽

**Unix 盆栽**は、Unix・Linux などの作業環境を自分好みに少しずつ設定し、手入れし続けることを、盆栽の育成や剪定になぞらえた表現。特定のソフトウェア名や厳密な技術用語ではない。特に設定ファイルの手入れは「**dotfiles 盆栽**」とも呼ばれる。[dotfiles のこだわりを晒す](https://www.m3tech.blog/entry/dotfiles-bonsai)

## 何を手入れするか

- **シェル**：`.zshrc` などでエイリアス、補完、プロンプト、履歴を調整する。
- **エディタ**：キーバインド、プラグイン、[[エディタやターミナルの配色テーマ|配色テーマ]]、フォントを整える。
- **デスクトップ**：ウィンドウ配置、パネル、ショートカット、[[KRunner]] などを調整する。
- **スクリプト**：繰り返す操作をまとめ、必要に応じて追加・整理する。

実用性を高める作業でもあり、設定そのものを楽しむ趣味でもある。不要になった設定を削ることも、盆栽でいう「剪定」にあたる。

## dotfiles と ricing

**dotfiles** は、`.zshrc` や `.vimrc` のようなドットで始まる設定ファイルを指す言葉。設定を Git リポジトリで管理し、環境を移す人もいる。現在は `~/.config/` 以下の設定などもまとめて dotfiles と呼ばれることがある。[dotfiles の実例](https://www.m3tech.blog/entry/dotfiles-bonsai)

英語圏の **ricing** は、特にデスクトップの配色、フォント、ウィンドウ配置などを自分好みにカスタマイズする文化を指すことが多い。Unix 盆栽と重なるが、盆栽は見た目だけでなく、操作や設定を長く育てることにも使える比喩であり、完全な同義語ではない。[dotfiles 研究](https://martina.lindorfer.in/files/papers/dotfiles_msr23.pdf)

## ネットワークまわりの盆栽例

接続先・名前解決・通信の確認方法などを、自分の環境に合わせて少しずつ整える例。ここでは **Linux／Ubuntu 系**を中心にする。Unix 系でも OS や採用しているネットワーク管理ソフトによってコマンドは異なる。

### 何を育てるか

| 対象 | 手入れの例 |
| --- | --- |
| SSH | 接続先の別名やユーザー名を登録し、長い接続コマンドを短くする |
| 接続状況 | IP アドレス、経路、DNS を確認する手順をまとめる |
| 名前解決 | どの DNS サーバーが使われているか調べ、ネットワークごとの差を把握する |
| HTTP | `curl` でステータスや応答時間を確かめるコマンドを用意する |
| 自宅ネットワーク | ルーターや自宅サーバーの名前・用途・接続手順を記録する |
| VPN・プロキシ | 接続先や使う場面を整理し、接続後の DNS や経路も確認する |

### 例1：SSH 接続先に名前を付ける

自分の `~/.ssh/config` に、接続先ごとに設定を書く。以下のホスト名・ユーザー名は例なので、実際の環境に合わせる。

```sshconfig
Host home-server
    HostName server.example.net
    User alice
    ServerAliveInterval 30
    ServerAliveCountMax 3
```

`ssh home-server` で接続できる。`ServerAliveInterval` は応答がない間に確認メッセージを送り、`ServerAliveCountMax` は無応答を何回まで許すかを指定する。接続を必ず維持する設定ではない。[OpenSSH: ssh_config](https://man.openbsd.org/ssh_config)

鍵認証やホスト鍵の検証は有効に保ち、秘密鍵を dotfiles に入れない。設定を編集する前にバックアップし、接続できるうちに別ターミナルから試す。

### 例2：接続状況の確認をまとめる

```sh
ip -br address
ip route
resolvectl status
```

順にインターフェースとアドレス、**IPv4** の経路、DNS の状態を見る。IPv6 の経路は `ip -6 route`。`resolvectl` は systemd-resolved を利用する環境向けで、ない環境では使えない。NetworkManager を使っている場合は `nmcli connection show --active` でも有効な接続を確認できる。[resolvectl](https://www.freedesktop.org/software/systemd/man/255/resolvectl.html)、[NetworkManager: nmcli](https://networkmanager.dev/docs/api/latest/nmcli.html)

よく使う確認をシェルの関数やスクリプトにまとめれば、ネットワークが変わったときに同じ手順で比較できる。表示には IP アドレスや社内ドメインが含まれることがあるため、共有前に確認する。

### 例3：DNS と HTTP を切り分ける

```sh
resolvectl query example.com
curl -I --max-time 10 https://example.com/
```

前者は名前解決、後者は HTTP のヘッダー取得を試す。**どちらも外部に問い合わせを送る**。`curl -I` は HEAD リクエストなので、サーバーが HEAD を許さない・GET と異なる応答を返す場合がある。DNS が成功しても HTTPS が成功するとは限らず、その逆も環境によってはあり得る。対象を自分のサービスに替えるときは、問い合わせ先と機密情報に注意する。

### 例4：接続先の台帳を作る

自宅サーバーやルーターについて、役割、ホスト名、接続方法、障害時に確認する場所をノートにまとめる。IP アドレスを固定と決めつけず、DHCP や DNS の管理場所も記録すると復旧に役立つ。公開用の記録には秘密鍵、パスワード、API キー、VPN の秘密設定を載せない。

### 手入れの注意

- DNS・ファイアウォール・ルーティングの変更は通信を切断し得る。現在の設定と戻し方を先に記録し、リモート接続中は特に注意する。
- `curl` や DNS の問い合わせ、接続テストはネットワークに通信を発生させる。無関係なホストに大量のテストやスキャンをしない。
- 上の例は説明用であり、この環境には適用・動作確認していない。


## 手入れの注意

- 一度に大きく変えず、変更前の設定を保存し、少しずつ試す。
- 他人の設定やインストールスクリプトは、実行前に内容と依存関係を読む。
- 公開リポジトリに API キー、トークン、個人情報を含めない。Git に追加する前に差分を確認する。
- 環境依存の設定や復旧手順をメモし、新しい環境で再現できるようにする。

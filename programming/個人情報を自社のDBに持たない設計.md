# 個人情報を自社のDBに持たない設計

エブリーの技術ブログの記事「**個人情報を自社のDBに持たない設計は、どこまでできるのか**」（新谷、2026 年 10 月 30 日）のまとめ。

**結論**：個人情報をまったく持たないのは難しい。それでも、**任せられるものは外部（認証は IDaaS、決済は決済代行）に任せ、残るものは減らして切り離す** と、自社で守る範囲をかなり小さくできる。

| 区分 | もの | 自社の DB に残るもの |
| --- | --- | --- |
| **外部に任せきれる** | パスワード・MFA、クレジットカード番号、コンビニ払いなどの決済 | `sub`、決済のトークン・取引 ID |
| **一部だけ任せられる** | メールアドレス、氏名・住所、管理画面の検索 | 使い方しだい |
| **自社に残る** | 外部サービスの ID、利用履歴 | そのもの |

## DB に持たないことで防げること・防げないこと

**防げる**：DB に ID やトークンしかなければ、次のときに個人情報が漏れない。
- DB そのものが漏れたとき
- DB のコピー（分析用、開発環境）が漏れたとき
- DB にさわれる人が悪用したとき

**防げない**：DB に入る前や、DB の外で盗まれる場合。
- 入力ページの JavaScript が改ざんされる
- XSS やセッションの乗っ取り
- 入力した値が、ログやエラー通知に残る
- 外部サービス側の事故
- アプリのサーバーが乗っ取られ、IDaaS の API を悪用される → API サーバーに与える **IDaaS の権限をしぼる**、API の呼び出しを **監視** する

## どこまでが個人情報か

- 個人情報保護法では、それだけで個人が分かる情報のほか、**ほかの情報と簡単に照合できて** 個人が分かるものも個人情報になる
- IDaaS のユーザー識別子 **`sub`** には名前もメールもない。しかし、自社は IDaaS の管理画面や API で照らし合わせられる。だから、**`sub` にひもづく利用履歴は、個人情報として扱われる可能性が高い**
- くわしい基準は、個人情報保護委員会のガイドライン（通則編）

## 外部に任せきれるもの

### パスワードと MFA
- **Auth0、Amazon Cognito、Firebase Authentication** などの IDaaS が、パスワードのハッシュと MFA の情報を持つ
- OIDC を使えば、アプリは ID トークンの **`sub` だけ** をキーとして保存すればよい
- よい点：ハッシュの漏えいや、パスワードの使い回しへの攻撃（リスト型攻撃）の危険が減る。MFA やパスキーを自分で作らなくてよい

### クレジットカード
- **割賦販売法** で、カードを扱う加盟店は、カード番号を適切に管理しなければならない。方法は **非保持化** か **PCI DSS に準拠** するか。PCI DSS は要件が多いので、ほとんどが非保持化を選ぶ
- カード番号がどこを通るかで、3 つのつなぎ方がある

| 方式 | 流れ | 非保持化 |
| --- | --- | --- |
| **リンク型** | 決済代行のページに移って、そこでカード番号を入れる | ○ |
| **JavaScript 型** | 加盟店のページに置いた決済代行のスクリプトが、ブラウザーから決済代行へ直接カード番号を送り、**トークン** を受け取る。番号は自社のサーバーを通らない | ○ |
| **パススルー型** | 自社のサーバーでカード番号を受け取り、決済代行へ送る | ×（非保持化の要件を満たさない） |

- JavaScript 型でも、**入力ページのスクリプトが改ざんされると、入力した時点で盗まれる**。入力ページは守る必要がある
- 表示用に、**下 4 けたとブランド** を持つのは危険が小さい
- PCI DSS では、**セキュリティコードは承認のあとに保存してはいけない**

### そのほかの決済
- コンビニ払い・キャリア決済・QR コード決済は、ふつう決済代行の側で完結する。自社に残るのは **取引 ID** だけ

### アプリ内課金
- iOS・Android アプリのデジタルコンテンツは、App Store・Google Play が決済する
- サーバーが受け取る **取引 ID や購入トークン** は、ユーザーにひもづくので、自社のデータとして残る

## 一部だけ任せられるもの

### メールアドレス
- IDaaS はログイン ID としてメールを持つ。ログイン中のユーザーなら、ID トークンから読める
- 一斉に通知を送るには IDaaS の API を何度も呼ぶことになり、数が多いと **レート制限** にかかる
- IDaaS のメール機能は、確認コードやパスワードの再設定など **認証のため** のもの。ふつうのお知らせには使えない
- 自社の DB には `sub` だけを持ち、必要なときに IDaaS から取ってくれば、**情報のもとが 1 か所** になる

### 氏名・住所
- 氏名は ID トークンから表示でき、IDaaS の標準属性にも保存できる
- 住所・電話番号・プロフィールを IDaaS に入れるのは、ふつう **すすめられていない**
  - Auth0 の文書：メタデータには認証に関係するデータだけを入れる
  - Cognito の文書：よく変わるデータは別のデータストアに入れる
- **IDaaS は認証のためのもので、アプリの DB の代わりではない**。重複や不適切なことばのチェックが要る **表示名** は、自社の DB に持つほうがよい

### 管理画面の検索
- Cognito の **`ListUsers`** で検索できるのは、一部の標準属性だけ。しかも **完全一致か前方一致** だけ。名前の部分一致で探すには、全員を取ってきて手元でしぼるしかない
- 制限：1 回で最大 **60 件**、一覧の API は 1 リージョンで毎秒 **30 回** まで → 毎秒最大 **1,800 人**

| ユーザー数 | 全員を取るのにかかる時間 |
| --- | --- |
| 1 万人 | 約 6 秒 |
| 100 万人 | 9 分あまり |

- 数万人で、前方一致で足りるなら、Cognito の検索でもよい。それより大きいなら、検索に使う属性を自社の DB か、メインと別の専用の DB に持つ

### 個人情報専用の保管庫（PII ボールト）
- **Skyflow** などの **データプライバシーボールト** は、個人情報を外に保管し、アプリには **トークン** を返す。表示するときにトークンをもとの値にもどす（**デトークン化**）。カードのトークンの考えを、カード以外の個人情報に広げたもの
- IDaaS より優れる点：**項目ごとのアクセス制御**、**一部を伏せた表示**、**だれがいつ見たかの記録**。海外の金融・医療で使われている
- 弱い点：表示のたびに往復が要る。住所で探すことが、自社の DB だけではできない。トークンにひもづく利用履歴は、`sub` と同じく個人情報になる

## 自社に残るもの

### 外部サービスの ID
- IDaaS の `sub` や、決済代行の顧客 ID は、自社に残すしかないキー
- **外部 ID と社内 ID の対応表** を、ほかの表と分けて持つ。ほかの表には社内 ID だけを入れる。ほかの表が漏れても、外部サービスと結びつけにくくなる

### 利用履歴
外に出せないので、**減らす**。
- **要らないものは持たない**。「この列がなかったら何が困るか」を考える
- **細かさを落とす**。年齢の確認だけなら、生年月日ではなく「20 歳以上」の旗だけを持つ
- **保存期間を決めて、自動で消す**。行を残して、個人が分かる列だけを空（NULL）にする方法もある。売上の合計などの集計は残せる

## 任せたあとも残る責任

### 委託先の監督
- 個人情報保護法では、個人情報の扱いを外に任せた会社は、**委託先を監督** しなければならない。IDaaS や決済代行は、ふつうこれにあたる
- 自分で監査に行くのは現実的でない。かわりに、**第三者の認証（SOC 2、ISO/IEC 27001）**、**データを置く場所**、**事故のときの通知の手順** を確かめる。Stripe や AWS は、認証や監査報告のページを公開している

### 削除の依頼
- IDaaS のアカウントを消すだけでは足りない。**利用履歴、ログ、分析用のデータ、決済代行の顧客情報** も扱う
- **論理削除**（削除の旗を立てるだけ）では、データは残る。物理的に消すか、もとにもどせない形で **個人が分からないようにする**
- **バックアップ** には、保存期間が終わるまで消したデータが残る。DB で消す時期とバックアップの保存期間を合わせておくと、消したデータがどこに残っているかを追いやすい

## 押さえどころ
- 外部に任せる基本：**パスワードは IDaaS、カード番号は決済代行（リンク型か JavaScript 型）**。自社には `sub` とトークンだけ
- `sub` だけでも、自社が照合できるので、**利用履歴は個人情報のまま**
- IDaaS は **認証のためのもの**。住所やプロフィールの置き場、検索の仕組みにはしない
- 残るものは、**対応表を分ける・持たない・細かさを落とす・期限で消す**
- 外に任せても、**委託先の監督** と **削除の依頼への対応** の責任は残る
- DB に持たなくても、**入力ページの改ざん・XSS・ログへの残り** では漏れる

# アプリ横断のコマンドパレット

VS Code のように、**現在のアプリの操作を文字で絞り込み、Enter で実行する**仕組みは、アプリの外側からも部分的に実現できる。ただし、すべてのアプリのすべての機能を共通 API から取得する方法はない。現実的には、アプリが公開するメニューを検索し、足りないものはアプリ自身のパレットや個別のショートカットで補う。

## まず区別する

| 種類 | 検索する対象 | 例 |
| --- | --- | --- |
| アプリ内パレット | アプリが登録した操作 | VS Code の Command Palette、Obsidian のコマンドパレット |
| メニュー検索・HUD | 今アクティブなアプリが外部公開するメニュー項目 | KDE の AppMenu を検索する拡張 |
| ランチャー | アプリ、ファイル、OS の操作、登録済みコマンドなど | [[KRunner]]、Windows の PowerToys Command Palette |

**ランチャーがアプリ名を検索できることと、前面のアプリの内部操作を検索できることは別。** メニュー検索でも、メニューに載っていない操作や、外部公開されていないアプリ独自の操作は通常見つからない。

## 「公開メニュー」とは

ここでの「公開メニュー」は、**アプリがメニューの項目や構造を、デスクトップ環境や別のプログラムから取得・操作できるように提供したもの**を指す説明上の言い方。インターネットに公開することでも、ソースコードが公開されていることでもない。

例えば、Dolphin の「ファイル → 新しいフォルダー」のようなメニューについて、アプリが項目名・階層・有効／無効などを外部に提供し、選択された項目を実行できるようにする。KDE のグローバルメニューはその情報をパネルに表示し、対応する HUD は同じような情報から項目を検索・実行できる。KDE では、ウィンドウに対応するメニューを D-Bus の `com.canonical.dbusmenu` などの仕組みで扱う。[KDE の AppMenu インターフェース](https://github.com/KDE/plasma-workspace/blob/master/appmenu/com.canonical.AppMenu.Registrar.xml)、[KDE の Wayland プロトコル](https://github.com/KDE/plasma-wayland-protocols/blob/master/src/protocols/appmenu.xml)

**画面上でメニューが見えることと、そのメニューが外部から取得できることは別。** アプリのツールキット、実装、デスクトップ環境、X11／Wayland などにより対応は変わる。逆に、外部公開されていても、そのアプリの全コマンドがメニューに含まれるとは限らない。

グローバルメニューに表示されるか試すと目安になるが、表示されない原因がウィジェットや環境設定にあることもあるため、それだけでアプリ非対応とは断定できない。アクセシビリティ API による取得は、メニュー公開とは別の経路。

## KDE Plasma で試す

[[KRunner]] のノートに記録された環境は **Plasma 5.27・X11** だった。ただし以前の記録なので、現在の環境を確認する。ターミナルでは次のように表示できる。

```sh
plasmashell --version
printf '%s\n' "$XDG_SESSION_TYPE"
```

### Plasma 5・X11

1. Plasma のパネルを右クリックしてウィジェットを追加し、**グローバルメニュー（Application Menu）**を置く。アプリを切り替えたとき、Dolphin などのメニューが表示されるか確認する。表示されないアプリは、この方式で検索できない可能性がある。
2. 候補として [krunner-appmenu](https://github.com/ArturGaspar/krunner-appmenu) がある。前面アプリのメニューを KRunner に表示するサードパーティ製プラグインで、README は Python・D-Bus・python-xlib を必要としている。**2024年にアーカイブ済み**であり、この環境での動作は未検証。
3. 導入する場合は、README とインストール・アンインストール用スクリプトの内容、依存関係、Plasma 5 との互換性を確認してから試す。導入後は検索設定でプラグインを確認し、対象アプリにフォーカスして KRunner を開き、「保存」などを入力して候補を選ぶ。実装の検索方式や日本語の部分一致の挙動は事前に保証できない。
4. まず保存などの安全な操作で試し、無効な項目やフォーカス移動後の対象アプリが正しいか確認する。削除などの操作は十分に確認してから実行する。

公開メニューを使うため、独自 UI のアプリ、Electron アプリ、ブラウザ内の Web アプリなどは対応がまちまち。グローバルメニューに項目が出ないアプリには、そのアプリ自身のパレットを使う方が確実。

### Plasma 6 の場合

[kde-appmenu-hud](https://github.com/mrlotfi/kde-appmenu-hud) は、前面アプリの公開メニューを KRunner からファジー検索して実行する別のサードパーティ製プラグイン。作者の説明では **Plasma 6・Qt 6** が必要で、X11 と Wayland に対応するが、Wayland の GTK アプリには制約がある。Plasma 5.27 用としては使えない。導入にはビルドとユーザーサービスの設定が含まれるため、内容を確認する。こちらも実機では未検証。

## メニューが公開されない場合

- **アプリ内蔵機能**：VS Code や Obsidian のように、独自のコマンドパレットを持つアプリではそれを使う。メニューにない操作も見つかる場合がある。
- **個別の操作を登録**：よく使うショートカットや CLI・API 操作を、ランチャーやスクリプトに登録する。キー送信の場合は対象ウィンドウとフォーカスを確認する。X11 と Wayland では操作可能な方法が異なる。
- **アクセシビリティ API**：Linux の AT-SPI が公開するメニューやボタンを列挙して検索・実行する方法もあるが、対応範囲はアプリに依存し、無効項目・動的なメニュー・誤操作への対策が必要。
- **画像認識や座標クリック**：公開 API がない場合の最終手段。画面配置や表示言語が変わると壊れやすい。

## 操作をランチャーに登録する具体例

以下は **KDE Plasma 5・X11 を想定**する例。以前の記録と現在の環境が同じか、前述のコマンドで確認する。実際の環境での動作は未検証で、設定やインストールは行っていない。

### 方法1：アプリケーションメニューに名前付き操作を作る

アプリが CLI を提供する場合は、キー送信より直接呼び出す方が安定しやすい。例として「Firefox で新しいタブを開く」を登録する。既存のタブの操作ではなく、Firefox を起動するか新しいタブを開く操作である。

1. まずターミナルで `firefox --new-tab about:newtab` を試す。Firefox の起動方法は環境によって異なる。
2. Plasma のアプリケーションランチャーを右クリックし、「アプリケーションを編集」を開く。
3. 適当なカテゴリで「新しい項目」を作り、名前を `Firefox 新しいタブ`、コマンドを `firefox --new-tab about:newtab` にして保存する。項目名は自由に変えられる。
4. [[KRunner]] を開き、`Firefox 新しいタブ` の一部を入力して候補を選択する。表示まで時間がかかる場合はランチャーを開き直す。アプリ検索が無効なら Plasma の検索設定で有効にする。

これは**決めておいた操作を名前で探す**方法であり、現在のアプリの全操作を自動的に一覧化するものではない。[KDE: メニュー項目の追加](https://docs.kde.org/trunk_kf6/en/kmenuedit/kmenuedit/quickstart.html)

### 方法2：スクリプトにまとめて登録する

複数の処理や長いコマンドは、自分のホームディレクトリに置いたスクリプトにまとめられる。たとえば `~/bin/firefox-new-tab` というファイルを作成する。

```sh
#!/bin/sh
exec firefox --new-tab about:newtab
```

保存後、ターミナルで実行権限を付け、直接動作を確認する。

```sh
chmod +x ~/bin/firefox-new-tab
~/bin/firefox-new-tab
```

問題なければ、方法1と同じメニュー編集画面で新しい項目を作り、コマンド欄にスクリプトの**絶対パス**（例：`/home/ユーザー名/bin/firefox-new-tab`）を指定する。`~/bin` がなければ先に作成する。ランチャーから実行するときは、ターミナルと `PATH` や環境変数が異なることがあるため、見つからない場合は実行ファイルも絶対パスで指定する。

### 方法3：既存アプリにキーを送る（X11）

アプリに CLI や API がなく、実行したい操作にショートカットがある場合の代替手段。例は Firefox のアドレスバーに移る `Ctrl+L` を送る。`xdotool` の導入が必要で、**Wayland のネイティブウィンドウにはそのまま使えない**。

```sh
xdotool search --onlyvisible --class firefox windowactivate --sync key --clearmodifiers ctrl+l
```

まず Firefox を起動し、ターミナルから単独で試す。複数ウィンドウがあると意図しないものが選ばれることがあるため、対象を確認する。動作すれば、このコマンドを方法1の項目として登録できる。操作の前にウィンドウを明示的に選ぶのは、KRunner 自身が一時的にフォーカスを持つため、単純に「現在のウィンドウ」にキーを送ると対象を誤ることがあるから。対象がないときやアプリのウィンドウクラスが異なるときは失敗する。[xdotool の説明](https://github.com/jordansissel/xdotool)

**注意**：キー送信はフォーカスやウィンドウ選択に左右される。特に削除・送信・保存などの操作では誤った対象に作用するおそれがあるため、上のような非破壊的な操作から試す。共通パレットで複数アプリを安全に扱うには、起動前の対象ウィンドウを記録し、実行直前に検証するなど追加の仕組みが必要。

### キーに直接割り当てる

検索せず一発で呼びたい操作は、Plasma 5 の「システム設定」→「ショートカット」→「カスタムショートカット」で**コマンド／URL**を実行するアクションを作り、キーを割り当てる方法もある。画面名は環境によって異なる。既存のショートカットとの衝突に注意する。[KDE: Custom Shortcuts](https://docs.kde.org/stable5/en/khotkeys/kcontrol/khotkeys/khotkeys.pdf)

## 他の OS

- **macOS**：アプリのヘルプメニュー内の検索で、対応するアプリのメニュー項目を探せる。メニューバーを使わないアプリやメニューにない操作までは対象にならない。
- **Windows**：[PowerToys Command Palette](https://learn.microsoft.com/en-us/windows/powertoys/command-palette/overview) はアプリ・ファイル・コマンドなどのランチャーであり、それだけで任意のアプリ内部の全メニューを列挙できるわけではない。対象アプリの機能、拡張機能、または UI Automation を利用した別の仕組みが必要。

## 結論

以前の **Plasma 5.27・X11** 環境が今も同じなら、まずグローバルメニューへの対応を確認し、次に `krunner-appmenu` を検討するのが近道。対応しないアプリは個別に補う。OS や環境の変更、プラグイン導入はまだ行っていない。

# HTTPキャッシュの仕組み

HTTPキャッシュは、以前受け取ったレスポンスを保存し、条件に応じて再利用する仕組み。**通信自体を省く場合と、更新確認をして本文の再送だけを省く場合がある。**

## 二つの再利用

```text
保存済みのレスポンス
  ├─ 新鮮で再利用可能 → 保存した本文を使う
  └─ 検証が必要 → サーバーへ問い合わせ
                     ├─ 304 → 保存した本文を使う
                     └─ 200 → 新しい本文を受け取る
```

新鮮さの有効期間などは `Cache-Control` で制御する。例えば `max-age=3600` は鮮度寿命を3600秒とする指定で、残り時間は既に経過した時間も考慮する。

## ETagによる条件付きリクエスト

初回のレスポンスで、サーバーが内容を識別する `ETag` を付ける。

```http
HTTP/1.1 200 OK
ETag: "version-1"
Cache-Control: no-cache
```

再利用時は、クライアントが `If-None-Match: "version-1"` を送る。内容が変わっていなければ、サーバーは本文を伴わない `304 Not Modified` を返し、保存した本文が使われる。更新されていれば、新しい本文を含む `200 OK` が返る。

## 混同しやすい指定

| 指定 | 意味 |
| --- | --- |
| `no-cache` | 保存はできるが、再利用前に検証が必要 |
| `no-store` | そのレスポンスをキャッシュに保存しない |
| `private` | 共有キャッシュへの保存を認めない。ブラウザーなどの私用キャッシュは利用可能 |

`no-cache` を「保存禁止」と覚えない。共有キャッシュにはCDNなどがあり、利用者ごとに異なる内容では共有範囲も重要になる。[MDN：HTTP caching](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Caching)

## リクエスト数と転送量

`304` でも問い合わせの通信は発生する。本文を再送しないため転送量は減るが、サーバーへのリクエスト数がゼロになるわけではない。[[ウェブサイトのリクエスト数]]では、この違いを分けて数える。

## 自分のブラウザーで観察する

1. 開発者ツールのNetworkを開く。
2. `Disable cache` をオフにし、同じページを初回・再訪で比較する。
3. Status、転送量、`Cache-Control`、`ETag`、`If-None-Match` を確認する。
4. キャッシュを無効にした場合も測り、操作条件を記録する。

通常の再訪、再読み込み、強制再読み込みでは挙動が違う。以下は未測定の記録欄であり、実測結果ではない。

| 操作 | Status | 転送量 | キャッシュ由来の表示 |
| --- | --- | --- | --- |
| 初回 | 未測定 | 未測定 | 未確認 |
| 再訪 | 未測定 | 未測定 | 未確認 |
| 再読み込み | 未測定 | 未測定 | 未確認 |
